# Architecture

An overview for contributors. The reasoning behind hard-to-reverse choices is in [decisions/](decisions/). Domain terms (Heading, Section, Subtree,
TODO Keyword, TODO Sequence) are defined in [GLOSSARY.md](../GLOSSARY.md).

## Modules

```
org-core        plain Kotlin, no IntelliJ: lexer, parser, TODO rules, structural edits
   ▲
org-intellij    the plugin: file type, PSI, highlighting, folding, Structure View, actions, settings
   ▲ (compileOnly; composed into org-intellij's jar)
org-ideavim     optional IdeaVim adapter, loaded only when IdeaVim is installed
```

- **`org-core`** has no platform dependency, so the build itself keeps IntelliJ and IdeaVim out of it. It is tested
  with JUnit 5 against `test-fixtures/org/`.
- **`org-intellij`** owns `plugin.xml` and builds the installable ZIP. It never references IdeaVim classes; it reaches
  IdeaVim only through its own `insertModeProvider` extension point, which `org-ideavim` implements.
- **`org-ideavim`** is a classic IdeaVim `VimExtension`, declared through `<depends optional="true">IdeaVIM</depends>`,
  so the plugin loads and works without IdeaVim.

## Parsing

One grammar, in `org-core`, builds trees through a small `TreeBuilder` interface
([0001](decisions/0001-single-grammar-two-tree-builders.md)). In the IDE, `PsiBuilder` sits behind it and produces the
PSI; `org-core` has a plain builder for tests and edits. There is no second document model.

- The lexer is line-based and restarts only at line starts outside verbatim blocks
  ([0003](decisions/0003-line-lexer-every-token-visible.md)), so the editor highlighter relexes small ranges as you type.
- The lexer does not know TODO Keywords. The parser classifies a Heading's first word against the document's TODO
  Sequences (`#+TODO`, `#+SEQ_TODO`, `#+TYP_TODO`), so editing a `#+TODO` line re-highlights the file.
- Syntax authority is the Org Syntax spec; Emacs `org-element` (Org 9.8.7) breaks ties. The parser fixtures' expected
  trees are generated by Emacs (`scripts/gen-fixtures.el`), and [compatibility.md](compatibility.md) lists the
  differences.

## Highlighting, folding, Structure View

- The lexer highlighter colors markup. `OrgAnnotator` adds what needs the parser: Heading level, TODO Keyword, priority
  and done titles. Every color key except underline falls back to a key that color schemes define, so theme plugins
  color Org too.
- `OrgFoldingBuilder` folds Subtrees, Sections, drawers and blocks. Visibility cycling reads its state from the folds
  instead of remembering it ([0004](decisions/0004-visibility-from-fold-regions-and-hooked-editor-keys.md)).
  `OrgGutterMouseListener` makes the gutter arrow on a Heading line fold its whole Subtree.
- The Structure View is built from the PSI Subtrees.

## Editing

Every command follows the same path:

1. Take a text snapshot of the document (`OrgSnapshot`) and parse it with `org-core`.
2. Resolve the target (the Heading, Subtree or checkbox at the caret) and check preconditions, refusing with a hint
   (for example "Cannot move past parent").
3. Compute the smallest text edits (`StructureEdits`, `TodoEdits`, `CheckboxEdits`).
4. Apply them in one IntelliJ write command (`OrgCommands.apply`), so Undo and Redo treat it as one step.

The document is never rewritten for a small edit, and unknown constructs are preserved verbatim. TAB, Shift+TAB and Move
Statement Up/Down are wrapped with `editorActionHandler`s that act only on a Heading line of an Org editor and otherwise
call the platform's own handler ([0004](decisions/0004-visibility-from-fold-regions-and-hooked-editor-keys.md)).

## IdeaVim

IdeaVim has no buffer-local mappings, and an extension's handler cannot decline a key
([0002](decisions/0002-ideavim-global-mappings-with-org-guard.md)). So every command is a global `<Plug>(org-…)`
with no keys of its own; users map the ones they want. The handler acts when the editor holds an Org file and otherwise
replays the keys mapped to it without mappings. The integration is IdeaVim's `orgmode` option, set in `.ideavimrc`. Every call into IdeaVim is guarded (`IdeaVimCompat`): an IdeaVim
older than 2.28.0, or one that lacks an API, leaves the integration off instead of breaking the IDE.

## Tests

| Where | What |
|---|---|
| `test-fixtures/org/parser` | `.org` inputs with Emacs-generated expected trees, run by `org-core` and the PSI |
| `test-fixtures/org/edit` | golden edits: input with `<caret>` markers and expected output, run by `org-core` and the IDE actions (with Undo) |
| `org-core` tests | parser, edits, motions, a 1 MB document, random-mutation round trips |
| `org-intellij` tests | PSI, highlighting, folding, actions, Structure View, settings, IdeaVim mappings |
| `testWithoutIdeaVim` | the IDE tests again with IdeaVim disabled |
| `-PtestIdeaVimVersion=…` | the IDE tests against another IdeaVim release |
| `:org-core:jmh` | parse and Subtree-move benchmarks |

`scripts/check-edit-fixtures.el` runs the matching Emacs command on every edit fixture, so the expected outputs are
checked against Emacs too.
